# Спецификация: синхронизация на событиях (event sourcing)

Версия: 0.1 (черновик). Заменяет алгоритм «скачать весь файл и слить» из `SYNC_SPEC.md` (разделы 5–6) на журнал событий. Разделы 2–3 `SYNC_SPEC.md` (подключение, локальное хранение) остаются в силе. `TECHNICAL_SPEC.md` не меняется: пользовательская история движений по-прежнему не входит в v1, журнал событий — внутренний механизм синхронизации.

## 1. Принципы

- **Источник истины — журнал событий.** Каждое изменение данных — это событие. Текущее состояние (таблицы Room) — производная от журнала (read model).
- **События неизменяемы.** Однажды записанное событие не редактируется и не удаляется. Исправление делается новым событием.
- **Каждое устройство пишет только свои события.** Конфликтов записи на уровне файла нет: объекты разных устройств не пересекаются.
- **Слияние — это объединение множеств событий** по `eventId`, а затем детерминированная свёртка по порядку (раздел 6).
- **Операции, а не значения, где это важно.** Остаток (`quantity`) меняется дельтой (`StockAdjusted`), а не присваиванием. Это устраняет потерю одновременных правок.
- **Офлайн-first.** Событие пишется локально в той же транзакции, что и изменение read model. Сеть не нужна.

## 2. Идентификаторы и время

### 2.1. Идентификаторы
- `eventId` — UUID v4, генерируется на устройстве. Глобально уникален, используется для дедупликации.
- `deviceId` — UUID устройства (уже есть в `sync_state`).
- `aggregateId` — `uuid` сущности (`section-*`, `product`, `comment`), см. `SYNC_SPEC.md` раздел 4.
- `seq` — порядковый номер события на данном устройстве, начиная с 1, без пропусков.

### 2.2. Гибридные логические часы (HLC)
Системное время устройств расходится, поэтому порядок событий задаёт HLC:

- `hlc = (wallMs: Long, counter: Int, deviceId: String)`.
- При локальном событии: `wallMs = max(now, lastWallMs)`; если `wallMs == lastWallMs`, `counter = lastCounter + 1`, иначе `counter = 0`.
- При получении удалённого события `r` с HLC `h`: `wallMs = max(now, lastWallMs, h.wallMs)`, `counter` вычисляется аналогично и с учётом `h.counter`.
- Сравнение: по `wallMs`, затем `counter`, затем `deviceId` (лексикографически). Это даёт total order, одинаковый на всех устройствах.
- Текущее HLC устройства хранится в `sync_state` (`hlcWall`, `hlcCounter`).

## 3. Формат события

Событие — JSON-объект в UTF-8, по одной строке на событие (JSON Lines).

```json
{
  "v": 1,
  "eventId": "7c1f...-uuid",
  "deviceId": "a3d2...-uuid",
  "seq": 42,
  "hlc": {"wall": 1731000000123, "counter": 0},
  "author": "anna",
  "type": "ProductQuantityAdjusted",
  "aggregate": "product",
  "aggregateId": "f19e...-uuid",
  "payload": {"delta": -1}
}
```

- `v` — версия формата события. Читатель обязан понимать все версии ≤ своей; неизвестная более новая версия — ошибка «обновите приложение» (как `schema_version`).
- `payload` — поля, специфичные для типа. Неизвестные поля в payload игнорируются (вперёд-совместимость).
- Поле `author` — имя пользователя (`username`), для отображения «изменил: Анна».

### 3.1. Типы событий

| type | aggregate | payload |
|---|---|---|
| `SectionCreated` | section | `name`, `iconKey`, `sortOrder` |
| `SectionRenamed` | section | `name` |
| `SectionIconChanged` | section | `iconKey` |
| `SectionHidden` | section | `hidden: bool` |
| `SectionOrderChanged` | section | `sortOrder` |
| `SectionDeleted` | section | — |
| `ProductCreated` | product | `name`, `sectionId`, `iconKey?`, `expiresAt?`, `quantity?`, `unit?`, `dosage?`, `intakeFrequency?` |
| `ProductUpdated` | product | поля, которые изменились (частичное обновление: только переданные ключи) |
| `ProductMoved` | product | `sectionId` |
| `ProductQuantityAdjusted` | product | `delta: int` (может быть отрицательной) |
| `ProductQuantitySet` | product | `quantity: int?` (явная установка, например ручной ввод числа) |
| `ProductOutOfStockSet` | product | `outOfStock: bool` |
| `ProductShoppingListSet` | product | `inList: bool` |
| `ProductPrioritySet` | product | `priority: bool` (FR-P15) |
| `ProductBought` | product | — (семантика FR-SL2: убрать из списка, снять «закончился», quantity 0 → 1) |
| `ProductDeleted` | product | — |
| `CommentAdded` | comment | `productId`, `text` |
| `CommentEdited` | comment | `text` |
| `CommentDeleted` | comment | — |

Примечания:
- `ProductCreated` и `SectionCreated` ссылаются на родителя по `uuid`, а не по локальному `id`.
- `ProductBought` и каскадные эффекты (удаление раздела → предметы → комментарии) при свёртке не записываются отдельными событиями: они выводятся из одного исходного события. Это уменьшает число событий и делает свёртку детерминированной.
- Каскад удаления раздела выражается **одним** событием `SectionDeleted`. Свёртка сама помечает предметы и комментарии удалёнными (раздел 6.3).

## 4. Хранение в S3

### 4.1. Структура объектов

```
{householdId}/events/{deviceId}/{segmentStart}-{segmentEnd}.jsonl
{householdId}/snapshots/{snapshotId}.db        (раздел 7)
{householdId}/manifest.json                    (раздел 7)
```

- Сегмент — файл с событиями одного устройства с `seq` от `segmentStart` до `segmentEnd` включительно, в JSON Lines. Имя с ведущими нулями (`000000000001-000000000100.jsonl`), чтобы сортировка по имени совпадала с порядком.
- Сегмент неизменяем после загрузки. Новые события устройство пишет в новый сегмент.
- Размер сегмента: не более 500 событий или 1 МБ (что наступит раньше). Сегмент формируется при синхронизации из несинхронизированных событий.

### 4.2. Гарантии записи
- Загрузка сегмента — `PUT` с `If-None-Match: *`. Объект с таким именем не должен существовать: имя уникально (`deviceId` + диапазон `seq`).
- При 412 на `If-None-Match` сегмент уже загружен — считаем успешным, если содержимое совпадает (проверка по `ETag`/контрольной сумме через `HEAD`). Иначе — ошибка целостности.
- Устройство отмечает сегмент как отправленный только после успешного `PUT`.

### 4.3. Чтение
- `LIST` префикса `{householdId}/events/` даёт все сегменты всех устройств.
- Уже известные сегменты (по имени и размеру, сохранённым локально) не скачиваются повторно.
- Локальная таблица `remote_segment` хранит имя и подтверждённое состояние применённых сегментов.

## 5. Локальное хранение

Новые таблицы (не синхронизируются):

- `event` — журнал событий: `eventId` (PK), `deviceId`, `seq`, `hlcWall`, `hlcCounter`, `author`, `type`, `aggregate`, `aggregateId`, `payload` (TEXT JSON), `v`, `origin` (`local` | `remote`), `pushed` (0/1), `appliedAt`. Уникальный индекс `(deviceId, seq)`.
- `remote_segment` — `key` (PK), `size`, `appliedAt`.
- `sync_state` — дополняется `hlcWall`, `hlcCounter`, `lastSeq`.

Таблицы `section`, `product`, `comment` остаются как read model. В них сохраняются поля `uuid`, `updatedAt`, `updatedBy`, `deleted`, `deletedAt` из `SYNC_SPEC.md` раздел 4: они нужны для свёртки и отладки, но источник правды — `event`.

Инвариант: **каждая запись в read model выполняется в одной транзакции с вставкой события.** Локальная команда без события не выполняется.

## 6. Свёртка (projection)

### 6.1. Порядок
Все события (локальные и удалённые) сортируются по HLC: `(wall, counter, deviceId)`. Свёртка проходит по этому порядку и применяет каждое событие к состоянию.

Дедупликация: событие с уже известным `eventId` пропускается.

### 6.2. Правила применения

- `ProductQuantityAdjusted`: `quantity = max(0, quantity + delta)`. Если quantity стал 0 — `isOutOfStock = true`; если стал больше 0 и был 0 — `isOutOfStock = false` (правило `TECHNICAL_SPEC.md` 5.1). Если `quantity` был null — трактуется как 0.
- `ProductQuantitySet`: прямая установка. Побеждает по порядку HLC.
- `ProductUpdated`: применяется по полям. Конфликт одного поля — побеждает событие с большим HLC.
- Событие с `aggregateId`, которого ещё нет, но которое ссылается на существующего родителя — создаёт сущность. Событие для уже удалённой сущности (`deleted = true`) игнорируется, кроме `*Created`-подобных (восстановление не предусмотрено).

### 6.3. Каскады
- `SectionDeleted`: раздел помечается удалённым. Все предметы, которые в нём находятся **на момент применения** события, помечаются удалёнными вместе с их комментариями.
- `ProductMoved` в раздел, который уже удалён (по HLC применения), **отклоняется**: событие записывается в журнал со статусом `rejected`, предмет остаётся в прежнем состоянии. Предмет, которого не было в разделе на момент удаления и который туда попал позже, тоже удаляется каскадом только если его `ProductMoved` был применён раньше `SectionDeleted`. Правило одно и то же на всех устройствах, потому что порядок задаёт HLC.
- Команда «перенести в раздел» на устройстве не даёт выбрать удалённый раздел (локальная валидация), поэтому `rejected` возникает только при параллельных правках.
- `ProductDeleted`: предмет и его комментарии помечаются удалёнными.
- `CommentAdded` к удалённому предмету: игнорируется, событие помечается `rejected`.

Итог: свёртка детерминирована и не зависит от порядка прихода сегментов, потому что всё упорядочено по HLC.

### 6.4. Детерминированность
- Тест: применение одного и того же набора событий в разном порядке приёма даёт одинаковый результат.
- Тест: два устройства, обменявшись событиями, имеют идентичные read model.

## 7. Снапшоты и компакция

- Снапшот — SQLite-файл read model на момент HLC `H`, загруженный как `snapshots/{snapshotId}.db`, плюс метаданные в `manifest.json`: `snapshotId`, `hlcUpTo`, `createdBy`, `createdAt`, `schemaVersion`, `eventCountUpTo`.
- Устройство может создать снапшот, когда накопилось ≥ 5000 событий или прошло ≥ 30 дней с последнего снапшота.
- При первом подключении устройство скачивает последний снапшот и только события с HLC > `hlcUpTo`.
- Старые сегменты, полностью покрытые снапшотом, могут быть удалены. Удаление выполняет только устройство, которое создало снапшот, и только после того, как все известные устройства подтвердили его применение (поле `ackedBy` в манифесте). В v1 упрощённо: сегменты старше 90 дней, покрытые снапшотом, удаляются.
- `manifest.json` обновляется через `If-Match` (ETag), при 412 — повтор.

## 8. Алгоритм синхронизации

```
1. Проверка: подключение настроено, есть сеть.
2. LIST {householdId}/events/ и manifest.json.
3. Для каждого сегмента, которого нет в remote_segment:
     GET → валидация JSONL (каждая строка — JSON, v ≤ поддерживаемой, eventId уникален).
     Вставка событий в таблицу event (origin = remote) — ОДНОЙ транзакцией.
     Регистрация сегмента в remote_segment.
4. Пересборка read model от последнего снапшота (или с нуля), если появились события с HLC
   раньше уже применённых (out-of-order). Иначе — инкрементальная свёртка новых событий.
5. Локальные непушнутые события (pushed = 0) группируются в сегменты по правилам 4.1.
6. PUT каждого сегмента с If-None-Match: *. При успехе — pushed = 1.
7. При необходимости — создание снапшота (раздел 7).
8. Всё, кроме 6 и 7, — локально и откатываемо. Ошибка сети на шаге 6 не отменяет уже применённые удалённые события: они корректны и идемпотентны.
```

Отличия от старого алгоритма:
- Нет 412-цикла на одном объекте: каждый сегмент пишется своим ключом.
- `isDirty` = есть ли `event.pushed = 0`.
- Сеть нужна только для шагов 2, 3, 6, 7.

## 9. Ошибки

| Ситуация | Сообщение |
|---|---|
| Сегмент повреждён (не JSONL, не JSON) | «Файл событий в хранилище повреждён. Синхронизация отменена, локальные данные не изменены.» |
| Версия события новее | «Данные созданы более новой версией приложения. Обновите приложение.» |
| Сегмент с тем же именем, но другим содержимым | «Конфликт целостности в хранилище. Обратитесь к владельцу семьи.» |
| Нет сети на шаге 6 | «Изменения сохранены локально и будут отправлены при следующей синхронизации.» |

## 10. Безопасность
Без изменений относительно `SYNC_SPEC.md` раздел 8. Отдельно: события содержат `author` и текст комментариев; объекты в бакете без серверного шифрования (как и раньше, при SSE-S3 — шифруются).

## 11. Тестирование

- Unit: HLC (монотонность, сравнение, слияние часов с откатом системного времени).
- Unit: свёртка — все типы событий, каскады, `rejected`-события.
- Unit: детерминированность при перестановке событий (property-style: случайные перестановки одного набора).
- Unit: кодирование/декодирование JSONL, неизвестные поля, версии.
- Unit: сегментация и правила pushed.
- Room in-memory: инвариант «команда пишет событие в той же транзакции».
- Интеграция с MinIO: загрузка сегментов, повтор `If-None-Match`, LIST, снапшот.
- Ручной сценарий: два устройства, одновременный «−» на одном продукте (ожидаемый итог — две дельты).

## 12. Открытые вопросы
1. Нужен ли `ProductQuantitySet` при наличии дельт, или ручной ввод числа всегда можно выразить дельтой (вычислив разницу на устройстве)? Предложено: оставить оба, т.к. явная установка проще для пользователя.
2. Порог и правила компакции (раздел 7) — подтвердить на реальных данных.
3. Нужно ли показывать пользователю «отправлено / ожидает отправки» по событиям? Предложено: да, как счётчик на экране синхронизации.
