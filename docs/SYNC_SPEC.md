# Спецификация синхронизации через S3

Дополняет `TECHNICAL_SPEC.md`. Сервер приложения не используется. Синхронизация идёт напрямую между приложением и S3-совместимым хранилищем (AWS S3, MinIO, Yandex Object Storage, Selectel и т.п.).

## 1. Принципы

- Локальная база — один SQLite-файл на устройстве.
- Удалённое хранилище — один объект на семью: копия того же SQLite-файла. Все устройства семьи синхронизируют один общий набор данных (см. раздел 2.1).
- Имя пользователя не определяет путь к файлу; оно нужно только для авторства изменений.
- Синхронизация ручная: кнопка «Синхронизировать» на главном экране и в настройках. Фоновой синхронизации в v1 нет.
- Конфликты разрешаются на уровне строк при слиянии, а не перезаписью всего файла.
- Учётные данные S3 никогда не попадают в SQLite-файл и не загружаются в S3.

## 2. Стартовый экран (онбординг / настройки подключения)

При первом запуске, а также из «Настроек → Подключение», показывается форма:

| Поле | Тип | Правила |
|---|---|---|
| Имя пользователя | текст | 1–50 симв., не пусто. Автор изменений (`updatedBy`), отображается в интерфейсе («изменил: Анна») |
| Идентификатор семьи (`householdId`) | текст | 3–63 симв., нижний регистр, цифры, дефис (как имя бакета). Одинаковый на всех устройствах семьи. Префикс объекта в бакете |
| URL | текст | Полный URL эндпоинта, `https://`. Допускаются `http://` только для `localhost` / LAN с явным подтверждением |
| Название бакета | текст | 3–63 симв., нижний регистр, цифры, дефис (правила S3) |
| S3 Access Key | текст | не пусто |
| S3 Secret Key | пароль | не пусто, поле маскируется, кнопка «показать» |

Кнопки:
- **«Проверить подключение»**: выполняет `HeadBucket` и `GET` / `HEAD` тестового объекта. Показывает результат: успешно / неверный ключ / бакет не найден / нет сети / нет прав.
- **«Сохранить»**: активна только после успешной проверки или при явном «Сохранить без проверки».

Дополнительно (в разделе «Дополнительно», по умолчанию выключено):
- Регион (нужен для AWS, по умолчанию `us-east-1`).
- Path-style адресация (включена по умолчанию, нужна для MinIO и большинства S3-совместимых сервисов).

Хранение:
- Username, householdId, URL, bucket, region, path-style: в DataStore (Preferences).
- Access Key и Secret Key: в зашифрованном хранилище (Android Keystore + DataStore / EncryptedSharedPreferences). В логах и в экранах не показываются.
- Кнопка «Выйти / очистить подключение» удаляет ключи и настройки. Локальные данные при этом не удаляются (спрашивается отдельно).

## 2.1. Семья и общий набор данных

- Вся база приложения (разделы, предметы, комментарии, настройки данных) общая для всех членов семьи. Эта база — один объект `{householdId}/inventory.db` в бакете.
- `householdId` задаётся при первом подключении семьи. Каждое устройство семьи вводит тот же `householdId`. Устройства с разным `householdId` не сливаются.
- `username` нужен для поля `updatedBy` и для отображения, кто внёс изменение. На путь к файлу он не влияет.
- В v1 все члены семьи используют один ключ доступа к бакету. Права ключа ограничиваются префиксом `{householdId}/`.
- Если объекта в бакете ещё нет (404), первое устройство загружает свою локальную БД как начальную. Устройство с пустой локальной БД при наличии объекта скачивает его без подтверждения.
- В v1 одно устройство работает только с одним `householdId`.
- Персональные данные отдельных членов семьи в v1 не предусмотрены. Если понадобятся, потребуется отдельный объект или уровень пути; путь к объекту формировать через одну функцию, а не строкой в нескольких местах.

## 3. Локальное хранение

- Файл: `filesDir/inventory.db` (SQLite). Доступ через Room или напрямую через `SQLiteOpenHelper`; решение за разработчиком, требование — формат файла SQLite.
- Режим WAL включён. Перед копированием для загрузки выполняется `PRAGMA wal_checkpoint(TRUNCATE)` и копирование через `VACUUM INTO 'tmp.db'`, чтобы в S3 уходил целостный одиночный файл без `-wal` / `-shm`.
- Таблица `sync_state` (локальная, в той же БД, но не синхронизируется):
  - `remote_etag` — ETag последней известной удалённой версии;
  - `last_sync_at`;
  - `device_id` (UUID устройства, генерируется один раз).

## 4. Изменения в модели данных (для синхронизации)

Все синхронизируемые таблицы (`section`, `product`, `comment`) получают:

| Поле | Тип | Назначение |
|---|---|---|
| uuid | TEXT, UNIQUE, NOT NULL | Глобальный идентификатор. Вместо `id` для слияния. Внутренний `id` может остаться для связей, но связи между строками ссылаются на `uuid` |
| updatedAt | INTEGER (epoch ms) | Время последнего изменения. Основа для разрешения конфликтов |
| updatedBy | TEXT | `username` или `device_id` автора последнего изменения |
| deleted | INTEGER (0/1) | Мягкое удаление (tombstone). Строка не удаляется физически до «сборки мусора» |
| deletedAt | INTEGER? | Время удаления |

Правила:
- Все удаления (раздел, предмет, комментарий) — мягкие: `deleted = 1`, `deletedAt = now`, `updatedAt = now`.
- Все записи обновляют `updatedAt` и `updatedBy`.
- Системные разделы имеют фиксированные `uuid`: `section-food`, `section-chemistry`, `section-pills`, чтобы при первой синхронизации с двух устройств они не дублировались.
- Для связи предмета с разделом и комментария с предметом используются `uuid` (`sectionUuid`, `productUuid`).
- Таблица `schema_meta` содержит `schema_version`. Слияние работает только с файлами той же или более старой версии схемы; более новая версия — ошибка «обновите приложение».

## 5. Алгоритм синхронизации

Нажатие «Синхронизировать» запускает `SyncUseCase` в фоне, UI показывает прогресс и результат.

```
1. Проверка: подключение настроено, есть сеть.
2. Блокировка UI на время записи (запрет редактирования, но не чтения).
3. HEAD объекта {householdId}/inventory.db  → remoteEtag (или 404 = удалённой копии нет).
4. Если 404:
     - локальный файл копируется в S3 (PUT, If-None-Match: *), сохраняется etag, конец.
5. Если remoteEtag == local.remote_etag и локальные изменения отсутствуют:
     - «Уже синхронизировано», конец.
6. GET объекта → временный файл remote.db (проверка размера и SQLite-заголовка "SQLite format 3\0").
7. Открыть remote.db только для чтения, проверить schema_version.
8. Слияние remote.db → локальная БД в ОДНОЙ транзакции (см. раздел 6).
9. Слияние успешно: VACUUM INTO local_merged.db.
10. PUT local_merged.db в S3 с заголовком If-Match: <remoteEtag> (или If-None-Match: * если объекта не было).
     - 200: сохранить новый ETag в sync_state, заменить локальный файл на local_merged.db, конец.
     - 412 Precondition Failed: кто-то записал между шагами 3 и 10 → вернуться к шагу 3 (максимум 3 попытки).
11. Ошибка сети / 403 / 5xx: откат транзакции (локальные данные не меняются), сообщение пользователю.
```

Важно: шаги 8–9 не должны обновлять локальную БД «наполовину». Если любой шаг падает, локальная БД остаётся прежней.

## 6. Правила слияния

Слияние по каждой таблице, по ключу `uuid`:

| Случай | Результат |
|---|---|
| Строка есть только локально | Сохраняется |
| Строка есть только в удалённом файле | Добавляется локально |
| Строка есть в обоих, `updatedAt` совпадает и содержимое одинаково | Ничего не делается |
| Строка есть в обоих, у одной `updatedAt` больше | Побеждает версия с большим `updatedAt` (Last-Writer-Wins), целиком |
| `updatedAt` совпадает, содержимое отличается | Побеждает версия с большим `updatedBy` (лексикографически), детерминированно на всех устройствах |
| Одна версия удалена (`deleted = 1`), другая нет | Побеждает более новая по `updatedAt`. Удаление, которое новее редактирования, выигрывает |

Порядок слияния:
1. `section` — разделы.
2. `product` — предметы. Если раздел-родитель удалён победителем, предмет тоже помечается удалённым (каскад), даже если сам он был изменён позже. Исключение: предмет был перенесён в другой раздел (тогда его `sectionUuid` указывает на живой раздел).
3. `comment` — комментарии. Если предмет удалён, комментарий помечается удалённым.
4. Служебные поля `sync_state` не сливаются.

Дополнительно:
- Дубликаты имён разделов и предметов после слияния не объединяются автоматически, допускаются (в ТЗ уже сказано: предупреждение, а не запрет). Для разделов с одинаковым именем, созданных на разных устройствах, показывается предупреждение «Раздел с таким названием уже есть» при следующем открытии.
- Очистка «мусора»: tombstones старше 90 дней удаляются физически при синхронизации, только если они старше `last_sync_at` всех известных устройств. В v1 упрощённо: старше 90 дней.

## 7. Ошибки и диагностика

| Ситуация | Сообщение пользователю |
|---|---|
| Нет сети | «Нет подключения к интернету. Данные сохранены локально.» |
| 403 AccessDenied | «Нет доступа к бакету. Проверьте ключи и права.» |
| 404 NoSuchBucket | «Бакет не найден. Проверьте название и URL.» |
| 412 после 3 попыток | «Файл в хранилище меняется другим устройством. Повторите синхронизацию.» |
| Файл повреждён / не SQLite | «Файл в хранилище повреждён. Синхронизация отменена, локальные данные не изменены.» |
| Схема новее | «Файл создан более новой версией приложения. Обновите приложение.» |

В «Настройках → Синхронизация» показываются: время последней успешной синхронизации, результат последней попытки, кнопка «Синхронизировать».

## 8. Безопасность

- Только HTTPS. HTTP разрешён только по явному подтверждению для локальных адресов.
- Подпись запросов: AWS Signature V4 (через AWS SDK for Kotlin с кастомным `endpointUrl` или собственная реализация подписи).
- Рекомендация пользователю: создать отдельного IAM-пользователя / ключ, у которого права только на бакет и префикс семьи `{householdId}/` — `s3:GetObject`, `s3:PutObject`, `s3:HeadObject`, `s3:ListBucket` на нужный префикс. Это указать в экране подключения текстом.
- Файл БД хранится в S3 без серверного шифрования на стороне приложения. Опционально (v1.1): шифрование файла AES-256-GCM ключом, выведенным из пароля (PBKDF2/Argon2). В v1 — открытый SQLite в S3 при включённом серверном шифровании бакета (SSE-S3).
- Манифест приложения: `INTERNET` и `ACCESS_NETWORK_STATE` (для проверки сети). Больше сетевых разрешений нет.
- Ключи не пишутся в логи; в логах выводятся только коды ошибок HTTP.
- Cleartext-трафик запрещён в `network_security_config.xml`, кроме явно разрешённых localhost-адресов.

## 9. Требования к тестированию

- Unit-тесты слияния: все строки таблицы решений из раздела 6, отдельно для каждой таблицы, включая каскад удалений.
- Тест детерминированности: слияние A←B и B←A даёт одинаковый результат.
- Тест идемпотентности: повторная синхронизация без изменений ничего не меняет.
- Интеграционные тесты с MinIO в Docker: создание, загрузка, 412 при гонке, 404 при первом запуске, 403 при неверном ключе.
- Тест атомарности: сбой на середине слияния не меняет локальную БД.
- Ручной сценарий: два эмулятора, одна БД в MinIO, правки на обоих, синхронизация в разном порядке.

## 10. Изменения в плане работ

Добавляется этап между 2 и 3 (или параллельно с этапом 1):

- **Этап S1:** S3-клиент, подпись, экран подключения, проверка подключения, хранение ключей.
- **Этап S2:** поля `uuid`, `updatedAt`, `updatedBy`, `deleted` во всех сущностях, миграция.
- **Этап S3:** алгоритм синхронизации, слияние, тесты слияния, интеграция с MinIO.
- **Этап S4:** UI синхронизации, обработка ошибок, индикатор состояния.

## 11. Открытые вопросы

1. ~~Один пользователь = один объект, или несколько пользователей делят файл~~ **Решено:** один объект `{householdId}/inventory.db` на семью, все члены семьи делят файл (раздел 2.1).
2. Нужно ли шифровать файл на стороне клиента (см. раздел 8)?
3. Допустимо ли, что при первом подключении устройства с пустой локальной БД данные просто скачиваются без вопросов? Предложено: да.
4. Нужна ли кнопка «Отправить только локальную копию» / «Взять только удалённую копию» для ручного разрешения ситуаций?
5. Один ключ на всю семью упрощает настройку, но отзыв доступа для одного члена возможен только сменой ключа у всех. Нужны ли отдельные ключи на каждого члена семьи? Это потребует либо IAM-пользователей на каждого, либо собственного сервера выдачи доступа.
6. Как передать `householdId` и ключи новым членам семьи? Варианты: ввод вручную, текстовый код или QR-код, который содержит параметры подключения. Ключ в открытом коде передавать нельзя.
